# Use Cases — School Activities Hub

## Назначение

Документ описывает основные сценарии взаимодействия пользователей с School Activities Hub в рамках MVP.

Каждый Use Case содержит цель, участников, предусловия, основной и альтернативные сценарии, а также результат выполнения.

Границы MVP определены в [Vision & Scope](../01_vision_and_scope/vision_and_scope.md). Пользовательские потребности представлены в [User Story Map](user_story_map.md).

---

## Общие условия

- В системе предусмотрены три роли: ученик, учитель и родитель.
- Пользователи имеют существующие учётные записи и авторизованы.
- Ученик может управлять только собственными записями.
- Учитель может изменять и отменять только созданные им занятия.
- Родитель получает доступ к уведомлениям, связанным с его детьми.
- Для MVP одно занятие предназначено для одного школьного класса.
- Уведомления формируются внутри веб-приложения.

## Use Cases ученика

### UC-01. Просмотреть каталог занятий

**Связанные истории:** US-01, US-02

**Актор:** Ученик.

**Цель:** найти подходящее дополнительное занятие.

**Предусловие:** ученик авторизован.

**Основной сценарий:**

1. Ученик открывает каталог занятий.
2. Система отображает опубликованные предстоящие занятия.
3. Ученик выбирает фильтры по предмету, классу и/или дате.
4. Система отображает занятия, соответствующие выбранным фильтрам.
5. Ученик просматривает результаты.

**Альтернативный сценарий:**

- A1. По выбранным фильтрам занятия не найдены:
  1. Система отображает сообщение об отсутствии результатов.
  2. Ученик может изменить или сбросить фильтры.

**Результат:** ученик видит список подходящих занятий либо сообщение об отсутствии результатов.

### UC-02. Просмотреть карточку занятия

**Связанная история:** US-03

**Актор:** Ученик.

**Цель:** изучить информацию о занятии перед записью.

**Предусловие:** ученик авторизован.

**Основной сценарий:**

1. Ученик выбирает занятие в каталоге.
2. Система получает актуальные данные занятия.
3. Система отображает карточку с названием, описанием, предметом, классом, преподавателем, датой, временем и количеством свободных мест.
4. Ученик просматривает информацию.

**Альтернативные сценарии:**

- A1. Занятие не найдено: система показывает сообщение об ошибке и предлагает вернуться в каталог.
- A2. Свободных мест нет: система отображает занятие, но запись на него недоступна.
- A3. Занятие отменено после открытия каталога: система показывает актуальный статус и блокирует запись.

**Результат:** ученик получает актуальную информацию о занятии.

### UC-03. Записаться на занятие

**Связанная история:** US-04

**Актор:** Ученик.

**Цель:** стать участником дополнительного занятия.

**Предусловия:**

- ученик авторизован;
- занятие существует.

**Основной сценарий:**

1. Ученик открывает карточку занятия.
2. Нажимает «Записаться».
3. Система проверяет, что занятие опубликовано и ещё не началось.
4. Система проверяет, что занятие предназначено для класса ученика.
5. Система проверяет наличие свободных мест.
6. Система проверяет отсутствие активной записи этого ученика на занятие.
7. Система создаёт активную запись на занятие.
8. Система формирует внутренние уведомления ученику и связанным с ним родителям.
9. Система показывает подтверждение записи.

**Альтернативные сценарии:**

- A1. Занятие отменено, не опубликовано или уже началось:
  - Система отклоняет запись и показывает сообщение о недоступности занятия.

- A2. Занятие предназначено для другого класса:
  - Система сообщает, что запись на это занятие недоступна ученику.

- A3. Свободных мест нет:
  - Система сообщает, что все места заняты.

- A4. Ученик уже имеет активную запись:
  - Система сообщает, что ученик уже записан.

- A5. Свободное место занял другой ученик во время выполнения запроса:
  - Система отклоняет запись и показывает актуальное количество свободных мест.

- A6. Не удалось сохранить запись:
  - Система сообщает об ошибке.
  - Новая активная запись не создаётся.

**Результат:**

При успешном выполнении ученик получает активную запись. Количество активных записей не превышает лимит участников.

При отказе новая запись не создаётся.

**Примечание:** проверки наличия мест и повторной записи выполняются в момент сохранения с учётом возможных одновременных запросов.

### UC-04. Отменить запись на занятие

**Связанная история:** US-06

**Актор:** Ученик.

**Цель:** отказаться от посещения занятия.

**Предусловия:**

- ученик авторизован;
- у ученика есть активная запись на предстоящее занятие.

**Основной сценарий:**

1. Ученик открывает раздел «Мои занятия».
2. Выбирает занятие.
3. Нажимает «Отменить запись».
4. Подтверждает отмену.
5. Система проверяет принадлежность записи ученику и возможность отмены.
6. Система переводит запись в статус `cancelled` и фиксирует время отмены.
7. Система показывает подтверждение.

**Альтернативные сценарии:**

- A1. Запись уже отменена:
  - Система сообщает об отсутствии активной записи.

- A2. Занятие уже началось или завершилось:
  - Система сообщает, что отмена недоступна.

- A3. Пользователь пытается отменить чужую запись:
  - Система отклоняет операцию.

**Результат:** запись имеет статус `cancelled` и сохраняется в системе для истории. Освободившееся место снова доступно для записи.

### UC-05. Просмотреть свои занятия

**Связанная история:** US-05

**Актор:** Ученик.

**Цель:** узнать, на какие предстоящие занятия он записан.

**Предусловие:** ученик авторизован.

**Основной сценарий:**

1. Ученик открывает раздел «Мои занятия».
2. Система находит активные записи ученика на предстоящие занятия.
3. Система отображает список с названием, предметом, датой и временем занятий.
4. Ученик выбирает занятие для просмотра подробной информации или отмены записи.

**Альтернативный сценарий:**

- A1. Активных записей на предстоящие занятия нет:
  - Система отображает пустой список и предлагает перейти в каталог.

**Результат:** ученик видит свои актуальные будущие занятия.

## Use Cases учителя

### UC-06. Создать и опубликовать занятие

**Связанная история:** US-09

**Актор:** Учитель.

**Цель:** организовать дополнительное занятие и открыть запись учеников.

**Предусловие:** учитель авторизован.

**Основной сценарий:**

1. Учитель открывает раздел управления занятиями.
2. Выбирает действие «Создать занятие».
3. Система отображает форму создания.
4. Учитель указывает название, описание, предмет, класс, дату, время начала и окончания, лимит участников.
5. Нажимает «Опубликовать».
6. Система проверяет корректность заполненных данных.
7. Система создаёт занятие и связывает его с текущим учителем.
8. Занятие получает статус `published`.
9. Система показывает подтверждение публикации.

**Альтернативные сценарии:**

- A1. Не заполнены обязательные поля:
  - Система выделяет соответствующие поля и предлагает их заполнить.

- A2. Указаны некорректные дата, время или лимит участников:
  - Система показывает сообщение об ошибке и предлагает исправить данные.

- A3. Не удалось сохранить занятие:
  - Система сообщает об ошибке публикации.

**Результат:** опубликованное занятие появляется в каталоге и доступно для записи при соблюдении ограничений.

**Примечание:** сохранение черновиков не входит в пользовательские сценарии MVP.

### UC-07. Изменить занятие

**Связанная история:** US-10

**Актор:** Учитель.

**Цель:** актуализировать параметры созданного занятия.

**Предусловия:**

- учитель авторизован;
- занятие создано текущим учителем;
- занятие опубликовано и ещё не началось.

**Основной сценарий:**

1. Учитель открывает карточку созданного занятия.
2. Выбирает действие «Изменить».
3. Система отображает текущие параметры занятия.
4. Учитель вносит изменения.
5. Нажимает «Сохранить».
6. Система проверяет корректность данных и соблюдение бизнес-ограничений.
7. Система сохраняет изменения.
8. Если изменилась дата или время, система формирует уведомления ученикам с активными записями и связанным с ними родителям.
9. Система показывает обновлённую информацию.

**Альтернативные сценарии:**

- A1. Учитель пытается изменить чужое занятие:
  - Система отклоняет операцию.

- A2. Новый лимит участников меньше количества активных записей:
  - Система отклоняет изменение и предлагает увеличить лимит.

- A3. Учитель пытается изменить целевой класс занятия при наличии активных записей:
  - Система отклоняет изменение класса.

- A4. Введены некорректные дата или время:
  - Система показывает ошибку валидации.

- A5. Занятие уже отменено или завершено:
  - Система запрещает редактирование.

**Результат:** параметры занятия обновлены. Если изменилась дата или время, участникам доступны соответствующие уведомления.

### UC-08. Отменить занятие

**Связанная история:** US-11

**Актор:** Учитель.

**Цель:** отменить ранее опубликованное занятие.

**Предусловия:**

- учитель авторизован;
- занятие создано текущим учителем;
- занятие опубликовано и ещё не началось.

**Основной сценарий:**

1. Учитель открывает карточку созданного занятия.
2. Нажимает «Отменить занятие».
3. Система запрашивает подтверждение.
4. Учитель подтверждает отмену.
5. Система переводит занятие в статус `cancelled`.
6. Система прекращает возможность новых записей.
7. Система формирует уведомления ученикам с активными записями и связанным с ними родителям.
8. Система показывает подтверждение отмены.

**Альтернативные сценарии:**

- A1. Учитель отказался от подтверждения:
  - Операция прекращается, статус занятия не меняется.

- A2. Занятие уже отменено, завершено или началось:
  - Система отклоняет отмену.

- A3. Учитель пытается отменить чужое занятие:
  - Система отклоняет операцию.

**Результат:** занятие имеет статус `cancelled` и недоступно для новых записей. Существующие записи сохраняются для истории, а отменённое занятие не отображается как предстоящее активное занятие ученика.

### UC-09. Просмотреть участников занятия

**Связанная история:** US-12

**Актор:** Учитель.

**Цель:** увидеть список записавшихся учеников.

**Предусловия:**

- учитель авторизован;
- занятие создано текущим учителем.

**Основной сценарий:**

1. Учитель открывает созданное занятие.
2. Выбирает раздел «Участники».
3. Система получает список учеников с активной записью.
4. Система отображает ФИО ученика, класс и дату записи.

**Альтернативные сценарии:**

- A1. Активных записей нет:
  - Система отображает пустой список.

- A2. Учитель пытается посмотреть участников чужого занятия:
  - Система отклоняет запрос.

**Результат:** учитель видит актуальный список участников собственного занятия.

## Use Case уведомлений

### UC-10. Просмотреть внутренние уведомления

**Связанные истории:** US-07, US-13

**Акторы:** Ученик, родитель.

**Цель:** получить актуальную информацию о записи и изменениях занятий.

**Предусловие:** пользователь авторизован.

**Основной сценарий:**

1. Пользователь открывает раздел «Уведомления».
2. Система получает уведомления, адресованные текущему пользователю.
3. Система отображает список уведомлений с текстом и датой события.
4. Пользователь просматривает содержание уведомлений.

**События, вызывающие создание уведомлений:**

- успешная запись ученика на занятие;
- изменение даты или времени занятия;
- отмена занятия.

**Альтернативный сценарий:**

- A1. Уведомлений нет:
  - Система отображает сообщение об отсутствии уведомлений.

**Особенности доступа:**

- ученик видит только собственные уведомления;
- родитель видит только уведомления о занятиях связанных с ним детей;
- уведомления другого пользователя недоступны.

**Результат:** пользователь получает актуальную информацию о событиях, связанных с занятиями.

**Примечание:** создание уведомлений выполняется системой автоматически в рамках соответствующих сценариев. Отдельная отправка email, SMS или push-уведомлений в MVP не предусмотрена.

### UC-11. Просмотреть созданные занятия

**Связанная история:** US-08

**Актор:** Учитель.

**Цель:** получить список собственных занятий для дальнейшего управления.

**Предусловие:** учитель авторизован.

**Основной сценарий:**

1. Учитель открывает раздел «Мои занятия».
2. Система получает занятия, созданные текущим учителем.
3. Система отображает список с названием, предметом, классом, датой, временем и статусом.
4. Учитель выбирает занятие для просмотра, изменения, отмены или просмотра участников.

**Альтернативный сценарий:**

- A1. Учитель ещё не создавал занятия:
  - Система отображает пустой список и предлагает создать занятие.

**Результат:** учитель видит список созданных им занятий и может перейти к доступным действиям.

## Связь с другими артефактами

- **Vision & Scope:** определяет границы MVP и пользовательские роли.
- **User Story Map:** описывает пользовательские потребности и состав релиза.
- **Business Rules:** фиксирует ограничения, применяемые в сценариях.
- **BPMN TO-BE:** показывает целевой бизнес-процесс записи на занятия.
- **ERD:** описывает данные, необходимые для выполнения сценариев.
- **API Contract:** определяет интерфейсы взаимодействия клиентского приложения с системой.
- **Sequence Diagram:** детализирует взаимодействие компонентов при записи ученика на занятие.
